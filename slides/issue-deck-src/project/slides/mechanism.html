Where it breaks: the producer's decision for one unseeded photon object

1

type(92)? yes. The leg's first filter (HLT1Photon, triggerType 92) saved the object as TriggerCluster; PAT keeps every type.

2

pt > 15? yes. The unseeded leg requires Et > 22 GeV (18 GeV for the Diphoton30_18 paths).

3

coll('hltEgammaCandidates')? no. The stored label is hltEgammaCandidatesUnseeded::HLT. Without a wildcard the comparison is exact (TriggerObjectStandAlone::hasCollection falls back to TriggerObject::hasCollection).

4

Discarded before the bits. qualityBits is only evaluated for objects that pass sel; the duplicate merging only sees accepted objects. Bits 16 and 17 stay 0 in every event.

# triggerObjects_cff.py, Photon

sel = "type(92) && pt > 15 &&
       coll('hltEgammaCandidates')"
skipObjectsNotPassingQualityBits = True

// TriggerObjectTableProducer.cc, produce()

for (const auto &obj : trigObjs)
  for (const auto &sel : sels_)
    if (sel.match(obj)) { // fails here
      bits = sel.qualityBits(obj);
      if (bits != 0) selected.push_back(...);
    }

Same logic in 13_0_X, 13_3_X, 14_0_X, 15_0_X and master; only the bit width (32 bits up to 15_0_1, 64 bits from 15_0_2) and the merging rule changed.

The object is correct in every respect the selection tests, except the collection label. The comparison is exact because the selection string carries no wildcard; the StandAlone matcher would honour a star. The electron selection was given the second collection in June 2023 (PR 41827); the photon selection was not.

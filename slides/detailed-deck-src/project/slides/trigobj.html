What a NanoAOD trigger object is, and how analyses use the filter bits

branchmeaning
TrigObj_idobject type: 11 electron, 22 photon, 13 muon, 15 tau, 1 jet, 6 fat jet, 2 MET, 3 HT, 4 MHT
TrigObj_pt, eta, phithe HLT object's kinematics (for e/gamma: the supercluster)
TrigObj_l1pt, l1iso, l1chargethe matched L1 seed within a cone (type -98 for e/gamma)
TrigObj_l2ptthe matched L2 object where configured (muons, jets, MET)
TrigObj_filterBitsone bit per HLT filter the object passed, from a per-type list in triggerObjects_cff.py; 32-bit up to 15_0_1, 64-bit from 15_0_2

# sketch of a typical NanoAOD trigger match (awkward)

to   = events.TrigObj
ph   = to[to.id == 22]
leg2 = ph[(ph.filterBits >> 17) & 1 == 1]
# unseeded R9 leg: always empty today
dr   = photons.metric_table(leg2)
ok   = ak.any(dr < 0.1, axis=2)

A leg-by-leg efficiency, a trigger-matched tag-and-probe, or a HiggsDNA-style matching of both photons needs the bit of the last filter of each leg. For the sub-leading leg of the diphoton triggers that bit is never set, so the match always fails.

The table is produced by TriggerObjectTableProducer from the unpacked MiniAOD trigger objects. Each object type has its own selection string; an object is written only if it passes that string and sets at least one bit of that type.

The filter bits are the only way to know which HLT filter an object passed in NanoAOD, because the filter labels themselves are not stored. Everything therefore depends on the per-type selection admitting the objects that carry the labels.

What the later filters save: HLTGenericFilter tags the collection and uses type 81 when saveTags is on

// HLTrigger/Egamma/plugins/HLTGenericFilter.cc (master lines 28 to 32 and 139 to 159; same logic from 10_6_X on)

l1EGTag_ = iConfig.template getParameter<edm::InputTag>("l1EGCand");
...
if (saveTags()) {
  filterproduct.addCollectionTag(l1EGTag_);  // hltEgammaCandidatesUnseeded for the unseeded leg
}
// Set output format
int trigger_type = trigger::TriggerCluster;
if (saveTags())
  trigger_type = trigger::TriggerPhoton;          // 81 for every saved object
...
PrevFilterOutput->getObjects(TriggerCluster, recoCands);
if (recoCands.empty())
  PrevFilterOutput->getObjects(TriggerPhoton, recoCands);  // accepts either type from the previous filter

Collection. The saved reference points into the l1EGCand collection. For the unseeded last filters that is hltEgammaCandidatesUnseeded, which PAT turns into the label hltEgammaCandidatesUnseeded::HLT on the object.

Type. These filters save type 81 (TriggerPhoton). The object keeps the 92 it received from the first filter, because PAT attaches the type of every filter that accepted an object (next slide). So type(92) in NanoAOD passes, and the collection test is the only thing left to fail.

Unchanged for years. The same three statements are in the 10_6_X, 12_4_X, 12_6_X, 13_0_X, 13_3_X, 14_0_X, 15_0_X and master versions of the plugin (only the line numbers move).

HLTEgammaGenericQuadraticFilter.cc has the identical block at lines 118 to 135. The first version of my notes described line 143 as saving TriggerCluster; that was wrong and was corrected in the second pass: with saveTags true the type is TriggerPhoton, and the 92 comes from the leg's first filter.

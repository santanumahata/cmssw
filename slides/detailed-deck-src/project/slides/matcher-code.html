How coll('hltEgammaCandidates') is evaluated: no star, so an exact label comparison

// DataFormats/PatCandidates/src/TriggerObjectStandAlone.cc

bool TriggerObjectStandAlone::hasCollection(
    const std::string &collName) const {
  // Move to wild-card parser, if needed only
  if (collName.find(wildcard_) != std::string::npos) {
    if (hasAnyName(collName, {collection()}))
      return true;
    ...  // label / instance / process with wildcards
    return false;
  }
  // Use parent class's method otherwise
  return TriggerObject::hasCollection(collName);
}

// DataFormats/PatCandidates/src/TriggerObject.cc, 54 to 71

bool TriggerObject::hasCollection(
    const std::string& collName) const {
  if (collName == collection_) return true;
  const edm::InputTag collectionTag(collection_);
  const edm::InputTag collTag(collName);
  if (collTag.process().empty()) {
    if ((collTag.instance().empty()
        && collectionTag.instance().empty())
        || collTag.instance() == collectionTag.instance()) {
      return (collTag.label() == collectionTag.label());
    }
  }
  return false;
}

Evaluated for the unseeded object: collName = hltEgammaCandidates, collection_ = hltEgammaCandidatesUnseeded::HLT. No star, so the base method runs; labels hltEgammaCandidates and hltEgammaCandidatesUnseeded differ; the result is false.

Wildcards do exist (the Run 2 muon selection writes coll('hlt*L3MuonCandidates')), so coll('hltEgammaCandidates*') would also have worked. The explicit OR of the two names was chosen for the fix because it names exactly the two collections.

filter('...') behaves the same way through hasFilterOrCondition: wildcard parser when the pattern contains a star, otherwise an exact match against the unpacked filter labels. The string cut calls the StandAlone overrides because the selector is templated on pat::TriggerObjectStandAlone.

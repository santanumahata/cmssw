The unseeded diphoton leg never gets its NanoAOD filter bits

Photon TrigObj_filterBits 16 and 17 (14 and 15 before NanoAOD v15) are documented for HLT_Diphoton30_22_R9Id_OR_IsoCaloId_AND_HE_R9Id_Mass90 / Mass95, but no photon trigger object ever carries them. Why it happens, how widespread it is, and the one-line fix.

Santanu Mahata · 4 November 2026
Checked against cms-sw/cmssw master ed35654b1 (today), release branches 13_0_X to 16_1_X, and the 2018 to 2026 HLT menus

PhysicsTools/NanoAOD/python/triggerObjects_cff.py

Context: the sub-leading photon of the main H to gamma gamma triggers cannot be trigger-matched from NanoAOD because the photon trigger-object selection drops every object that comes from the unseeded e/gamma collection. This deck walks through the trigger, the data path, the exact failing line, the scope across versions and menus, a scan of the whole trigger-object table, and the fix.

Orange boxes: the unseeded last filters NanoAOD discards. Bits in v15 numbering; v12 to v14: 12, 13, 15, 14.

The seeded leg runs on hltEgammaCandidates (L1-seeded superclusters, Et above 30 GeV). The unseeded leg runs on hltEgammaCandidatesUnseeded, built from all ECAL clusters without an L1 seed, Et above 22 GeV; its first filter is an HLT1Photon with triggerType 92. Each leg ends in two alternative last filters (R9, or cluster shape plus isolation); the leg combiner ORs them and the HLTEgammaAllCombMassFilter requires the pair mass above 90 or 95 GeV. NanoAOD defines one filter bit per last filter. The seeded ones work; the unseeded ones can never be set.

From the HLT filter to TrigObj_filterBits: the object survives four hand-offs and dies at the fifth

1 · HLT filters (saveTags)

The unseeded last filters tag their objects with the collection hltEgammaCandidatesUnseeded; the leg's first filter saves them with type 92, the later ones with type 81.

2 · hltTriggerSummaryAOD

Objects are stored once per HLT collection; every filter that accepted an object records its key and the type it saved it with.

3 · patTrigger → slimmedPatTrigger (MiniAOD)

The pat object keeps the collection label hltEgammaCandidatesUnseeded::HLT, all its types (92 and 81) and the labels of every filter it passed.

4 · unpackedPatTrigger (NanoAOD)

Filter labels are unpacked; the object reaches the table producer intact, with its collection name and types.

5 · triggerObjectTable, Photon selection

sel = type(92) && pt > 15 && coll('hltEgammaCandidates') is evaluated before the quality bits. The collection test fails, the object is dropped, and bits 16 and 17 are never computed.

Every step up to the table producer is correct: the objects are in MiniAOD, with the right collection name, both types and all filter labels. The Electron selection has accepted hltEgammaCandidatesUnseeded since June 2023 and populates its unseeded CaloIdL_MW bit in production, which proves the objects are there. Only the Photon selection string excludes them.

Where it breaks: the producer's decision for one unseeded photon object

1

type(92)? yes. The leg's first filter (HLT1Photon, triggerType 92) saved the object as TriggerCluster; PAT keeps every type.

2

pt > 15? yes. The unseeded leg requires Et > 22 GeV (18 GeV for the Diphoton30_18 paths).

3

coll('hltEgammaCandidates')? no. The stored label is hltEgammaCandidatesUnseeded::HLT. Without a wildcard the comparison is exact (TriggerObjectStandAlone::hasCollection falls back to TriggerObject::hasCollection).

4

Discarded before the bits. qualityBits is only evaluated for objects that pass sel; the duplicate merging only sees accepted objects. Bits 16 and 17 stay 0 in every event.

# triggerObjects_cff.py, Photon

sel = "type(92) && pt > 15 &&
       coll('hltEgammaCandidates')"
skipObjectsNotPassingQualityBits = True

// TriggerObjectTableProducer.cc, produce()

for (const auto &obj : trigObjs)
  for (const auto &sel : sels_)
    if (sel.match(obj)) { // fails here
      bits = sel.qualityBits(obj);
      if (bits != 0) selected.push_back(...);
    }

Same logic in 13_0_X, 13_3_X, 14_0_X, 15_0_X and master; only the bit width (32 bits up to 15_0_1, 64 bits from 15_0_2) and the merging rule changed.

The object is correct in every respect the selection tests, except the collection label. The comparison is exact because the selection string carries no wildcard; the StandAlone matcher would honour a star. The electron selection was given the second collection in June 2023 (PR 41827); the photon selection was not.

Bits 0 to 7 (single-photon HE filters), 9 to 13 (EB tight-ID filters and the Mu17_Photon30 photon leg) are fine. Decimal values of the dead unseeded bits: 65536, 131072, 524288 in v15 and master; 16384, 32768, 131072 in v12 to v14.

Of the 21 photon bits in master, three can never be set because of the collection test (16, 17, and 19 where its filter exists), and one more, bit 8, names an HT filter whose objects are never e/gamma objects. Bits 18 and 19 additionally name filter names that were changed in the 2023 menu. Everything else works where the filter exists in the menu of that year.

Menus

19 menu files checked, 2018 GRun to the frozen 2026 menu: the four Diphoton30_22 filters exist everywhere, always on the same collections, with the same 16-filter chain. Path versions v13 (2018, early 2022) to v29 (2026).

Datasets

Every Run 3 NanoAOD file: 2022 to 2025 data (PromptNano, 22Sep2023, 16Dec2023, v15 re-NANO) and the Summer22, 22EE, 23, 23BPix and 24 MC campaigns, plus any Run 2 input re-processed with v12 or later.

Analyses

Any NanoAOD-based matching of the sub-leading photon finds nothing: HiggsDNA-style workflows, the HYgammaRunIII legend that lists bits 16 and 17 as the legs, FLAF configurations. MiniAOD-based flashgg reads the objects directly and is unaffected.

Verified today on the live upstream repository: master ed35654b1 (the newest commit as of 4 November 2026), the branch tips 14_1_X, 14_2_X, 15_0_X, 15_1_X, 16_0_X and 16_1_X, and the newest tags CMSSW_16_1_3 and CMSSW_16_0_10 all carry the seeded-only photon selection. GitHub shows no open pull request or issue about it. The defect entered with PR 40711 in February 2023, which added the bits; the electron selection got the second collection in June 2023 (PR 41827), the photon one did not.

Same mechanism elsewhere

Only in the Photon list: the three unseeded diphoton bits and bit 8, whose filter saves HT objects. Electron and Muon have no collection mismatch. Two whole tables were empty by configuration: MET in every version since v9, and BoostedTau in v12 to v14, whose selection required a filter name ending in ParticleNetTauTau while the menus end in 0p30 or Tag0p03 (relaxed in 15_0_2).

Stale names are the common case

One bit list serves the 2022 to 2026 menus, so bits for filters that were renamed or retired stay documented but silently empty for later years, and bits added for new filters are empty for earlier years. That is a different, documentation-level problem; the photon one is a code defect that no menu can cure.

Method: every mksel entry of triggerObjects_cff.py (master, v15, v13 and v12 versions) was resolved against the frozen 2022 v1.2 and v1.4, 2023, 2024, 2025 and 2026 menus plus the development GRun menus. For each matched filter module the collection its objects come from was read from the menu (l1EGCand, inputTag, CandTag, originTag and so on) and compared with the coll() terms of the selection. The scanner is in the notes repository as scripts/deadbits.py.

The fix: one line, mirroring what the Electron selection has done since 2023

PhysicsTools/NanoAOD/python/triggerObjects_cff.py, Photon = cms.PSet( ... )

- sel = cms.string("type(92) && pt > 15 && coll('hltEgammaCandidates')"),

+ sel = cms.string("type(92) && pt > 15 && (coll('hltEgammaCandidates') || coll('hltEgammaCandidatesUnseeded'))"),

Why this form

It names exactly the two e/gamma collections and copies the Electron selection (PR 41827). A wildcard coll('hltEgammaCandidates*') would also match, but would silently admit any future collection with that prefix.

What changes in the output

Unseeded objects enter the photon branch. With skipObjectsNotPassingQualityBits on, only those that set a photon bit are written, and the only photon-bit filters on the unseeded collection are the three diphoton ones. A seeded twin in the same direction is merged with OR-ed bits; otherwise a second photon entry appears, as for electrons.

What does not change

Bit numbers, documentation strings, the other object types, the event content. Existing files cannot be repaired: the objects were never written. Only a new NANO pass with the fix restores the sub-leading leg.

Applies cleanly to today's master. Both branches are on the fork santanumahata/cmssw; nothing pushed to cms-sw/cmssw, no pull request opened yet.

The change is deliberately minimal so that the bit numbering and documentation stay stable and the pull request is easy to review. Everything else that the scan found, the HT filter in the photon list, the renamed 30_18 filters, the stale bits per year, is left to follow-up pull requests so that this fix is not held up.
